# Контракт equals и hashCode

## Сравнение по ссылке: `equals()` по умолчанию

* `==` — тупое сравнение по ссылке: разные ссылки — разные объекты, даже если все поля одинаковые.
* `equals()` по умолчанию — тоже тупое сравнение по ссылке. Вот он в [`Object`](Класс%20Object%20и%20его%20методы.md):
  ```java
  public boolean equals(Object obj) {
      return (this == obj);
  }
  ```
  То есть в него просто вшит оператор `==`.

Получается, что дефолтный `equals()` — это просто обёртка над оператором `==`. Результат такого сравнения всегда `false`, если не подать ему тот же самый объект. Поэтому, чтобы `equals()` работал так, как нужно нам как разработчикам, мы его переопределяем.

### Примитивы и ловушка кэша `Integer`

Для примитивов (`int`, `long`, `double`, `boolean`…) никаких ссылок нет, там `==` сравнивает сами значения — и это правильно. А вот с объектами есть ловушки, которые любят на собесах:

```java
Integer a = 127, b = 127;
System.out.println(a == b);      // true
Integer c = 128, d = 128;
System.out.println(c == d);      // false
```

Почему так? [Автоупаковка](../Синтаксис%20и%20типы/Классы-обёртки%20и%20автоупаковка.md) вызывает `Integer.valueOf()`, а он отдаёт объекты из кэша для чисел от `-128` до `127`. Поэтому `127` — это один и тот же объект, а `128` — два разных. Со строками похоже: литералы `"java"` лежат в [*пуле строк*](../Строки/Класс%20String%20—%20создание,%20сравнение%20и%20пул%20строк.md) и указывают на один объект, а `new String("java")` — всегда новый.

**Мораль простая:** объекты сравниваем через `equals()`, а `==` оставляем примитивам и проверке «это тот же самый объект?».

## Переопределяем `equals()`

### Что требует документация

Как говорит [документация `java.lang.Object`](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/lang/Object.html#equals(java.lang.Object)), `equals()` должен обладать следующими свойствами:

> - **Рефлексивность:** для любой ненулевой ссылки `x` вызов `x.equals(x)` должен возвращать `true`.
> - **Симметричность:** для любых ненулевых ссылок `x` и `y` вызов `x.equals(y)` должен возвращать `true` тогда и только тогда, когда `y.equals(x)` возвращает `true`.
> - **Транзитивность:** для любых ненулевых ссылок `x`, `y` и `z`, если `x.equals(y)` возвращает `true` и `y.equals(z)` возвращает `true`, то и `x.equals(z)` должен возвращать `true`.
> - **Согласованность:** для любых ненулевых ссылок `x` и `y` повторные вызовы `x.equals(y)` должны всегда возвращать `true` или всегда возвращать `false`. Условие: данные объектов, которые используются при сравнении в `equals`, не изменялись.
> - Для любой ненулевой ссылки `x` вызов `x.equals(null)` должен возвращать `false`.

Интересно, что дока сама предлагает обратить внимание на `hashCode()` и `HashMap`:

> **См. также:** `hashCode()`, `java.util.HashMap`

А ещё дока сама говорит нам про контракт:

> **Примечание к API:** Если вы переопределяете этот метод, как правило, нужно переопределить и метод `hashCode`. Так соблюдается общий контракт `hashCode`: у равных объектов должны быть одинаковые хеш-коды.
>
> **Требования к реализации:** Метод `equals` класса `Object` реализует самое строгое из возможных отношений эквивалентности на объектах. Для любых ненулевых ссылок `x` и `y` этот метод возвращает `true` тогда и только тогда, когда `x` и `y` ссылаются на один и тот же объект (то есть выражение `x == y` равно `true`). Иными словами, при сравнении по ссылке каждый класс эквивалентности состоит ровно из одного элемента.

### Реализация

Пример переопределения:

```java
@Override
public boolean equals(Object obj) {
    // проверка на рефлексивность: если сравниваем объект с самим собой, то всегда true
    if (this == obj) return true;
    // проверка пятого пункта: если сравниваем с null — false.
    // сам this никогда не бывает null: у null нельзя вызвать метод, мы бы словили NullPointerException раньше.
    // затем сравниваем принадлежность к одному классу: если объекты разных классов, они точно не равны — false
    if (obj == null || getClass() != obj.getClass()) return false;
    // теперь мы точно знаем, что исходный объект и поданный в метод — одного класса, можем смело кастить
    Programmer that = (Programmer) obj;
    // и сравнивать по полям. Кстати, сравнивать по каждому полю не обязательно:
    // мы сами решаем, каких полей достаточно, чтобы считать объекты одинаковыми.
    // Objects.equals() безопасен к null: два null равны, null и не-null — нет
    return salary == that.salary && Objects.equals(position, that.position);
}
```

`Objects.equals()` из последней строки внутри очень простой — вот он в [`java.util.Objects`](https://github.com/openjdk/jdk/blob/jdk-25-ga/src/java.base/share/classes/java/util/Objects.java#L61):

```java
public static boolean equals(Object a, Object b) {
    return (a == b) || (a != null && a.equals(b));
}
```

Сначала дешёвое `==` — оно же ловит случай, когда оба `null`, — и только потом `equals()`, причём у заведомо не-`null` объекта. Поэтому для полей-объектов удобнее звать его, а не `position.equals(that.position)`: тот упадёт с `NullPointerException`, если `position` — `null`.

### Наследование: вызываем `super.equals()`

В случае [наследования](Наследование.md) делаем точно так же, но с вызовом родительского `equals()`:

```java
@Override
public boolean equals(Object obj) {
    // сначала вызываем родительский метод через super и смотрим результат: если на уровне родителя объекты разные, сразу отдаём false.
    // А если на уровне родителя одинаковые, мы ещё не можем утверждать, что на уровне наследника тоже (наследник расширяет родителя своими полями)
    if (!super.equals(obj)) return false;
    // тут мы точно можем кастить, потому что у родителя была проверка getClass() != obj.getClass().
    // Интересно то, что getClass() выполняется у того объекта, у которого был вызван, а значит родитель проверяет, является ли obj объектом класса MiddleProgrammer, а не Programmer, как могло показаться, — подробнее в сноске
    MiddleProgrammer that = (MiddleProgrammer) obj;
    // дальше просто сравниваем по тем полям наследника, которые считаем нужными
    return grade == that.grade;
}
```

Почему родительский `getClass()` вдруг видит класс наследника — разобрано в сноске[^getclass].

### `instanceof` вместо `getClass()`

Если в нашей логике наследования допускается прямое сравнение родителя и наследника, то можем реализовать через `instanceof`:

```java
@Override
public boolean equals(Object obj) {
    if (this == obj) return true;
    if (!(obj instanceof Programmer)) return false; // null тоже отсекается
    Programmer that = (Programmer) obj;
    return Objects.equals(name, that.name);
}
```

И у наследника добавляется обязательная проверка на `instanceof`:

```java
@Override
public boolean equals(Object obj) {
    if (this == obj) return true;
    if (!(obj instanceof MiddleProgrammer)) return false; // своя проверка обязательна
    if (!super.equals(obj)) return false;
    MiddleProgrammer that = (MiddleProgrammer) obj;
    return level == that.level;
}
```

### Засада: так мы ломаем симметричность

А теперь проверим эту пару на свойства из документации. Возьмём `Programmer` и `MiddleProgrammer` с одинаковым именем:

```java
Programmer p = new Programmer("Вася");
MiddleProgrammer m = new MiddleProgrammer("Вася", 3);

p.equals(m); // true: m instanceof Programmer, имена совпали
m.equals(p); // false: p не instanceof MiddleProgrammer
```

`p` равен `m`, а `m` не равен `p` — **симметричность нарушена**. Это и есть тот самый «пример нарушения симметрии», который просят на собесах. Если попробовать починить это в наследнике («если сравнивают с простым `Programmer`, сравни только имя»), сломается уже транзитивность: два `MiddleProgrammer` с разным уровнем окажутся равны одному и тому же `Programmer`, но не равны друг другу.

Вывод такой: нельзя одновременно сравнивать родителя с наследником и добавлять в наследнике новые поля в `equals()`. Выбирать приходится одно из трёх:

| Подход | Как работает | Цена |
|---|---|---|
| `getClass()` | Объекты разных классов никогда не равны | Симметрия на месте, но наследник никогда не равен родителю, даже если «по смыслу» они одно и то же |
| `instanceof` + `final` `equals()` в родителе | Наследники не переопределяют сравнение и не добавляют в него поля | Подходит, только когда наследники отличаются поведением, а не данными |
| Композиция вместо наследования | `MiddleProgrammer` хранит `Programmer` внутри, а не расширяет его | Больше кода-обёртки, зато `equals()` у каждого класса свой и честный |

Третий вариант советует Джошуа Блох в [«Effective Java»](https://www.oreilly.com/library/view/effective-java-3rd/9780134686097/) — статья 10 как раз про контракт `equals`.

### А при чём тут Hibernate

Есть место, где `getClass()` подставляет подножку, — *JPA-сущности*. Hibernate при [ленивой загрузке](../../09%20Базы%20данных%20и%20доступ%20к%20данным/ORM%20и%20JPA/Ленивая%20загрузка,%20проблема%20N+1%20и%20скрытый%20SQL.md) подсовывает вместо сущности *прокси* — сгенерированный класс-наследник вроде `Programmer$HibernateProxy$…`. Для одной и той же строки в базе `getClass()` у прокси и у настоящей сущности разный, и `equals()` с проверкой `getClass()` скажет, что это разные объекты. Поэтому для сущностей обычно делают так:

* сравнение через `instanceof` (или через `Hibernate.getClass()`), а не через `getClass()`;
* сравнение по `id`, причём сущность без `id` (ещё не сохранённая) равна только самой себе;
* `hashCode()` — константа для класса (например, `getClass().hashCode()`), потому что `id` появляется только после сохранения, а хеш не должен меняться, пока объект лежит в `HashSet`;
* никаких ленивых коллекций в `equals()` и `hashCode()`, поэтому `@Data` и `@EqualsAndHashCode` из [Lombok](../../16%20Инструменты%20и%20инженерные%20практики/Инструменты%20разработчика/Lombok.md) на сущностях — опасная затея.

Подробно и с тестами этот подход разобран у [Vlad Mihalcea](https://vladmihalcea.com/the-best-way-to-implement-equals-hashcode-and-tostring-with-jpa-and-hibernate/).

> [!SUMMARY] Итого
> Метод `equals()` сравнивает объекты по их содержимому. Это нужно, чтобы понять, являются ли два разных программных объекта представлением одного и того же объекта из реального мира.

## Переопределяем `hashCode()`

### Что требует документация

Что говорит [документация](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/lang/Object.html#hashCode()):

> Общий контракт метода `hashCode`:
>
> - **Согласованность.** Если во время одного запуска Java-приложения метод вызывается на одном и том же объекте несколько раз, он должен каждый раз возвращать одно и то же целое число. Это верно, пока не меняются данные объекта, которые используются при сравнении через `equals`. Между разными запусками одного и того же приложения это значение может быть разным.
> - **Равные объекты дают равные хеш-коды.** Если два объекта равны по методу `equals`, то `hashCode` для каждого из них должен вернуть одно и то же целое число.
> - **Неравные объекты могут иметь одинаковый хеш-код.** Если два объекта не равны по методу `equals`, их хеш-коды не обязаны различаться. Однако программисту стоит помнить, что разные хеш-коды для неравных объектов могут повысить производительность хеш-таблиц.

Если кратко, то обещается, что у одинаковых объектов **одинаковый** `hashCode`, а у разных **не обязательно разный**: `hashCode()` возвращает `int`, а у `int` всего `4 294 967 296` возможных значений. А значит, *коллизий* не избежать — одинакового значения `hashCode` у разных объектов.

```java
@IntrinsicCandidate
public native int hashCode();
```

Вот так выглядит оригинальный нативный `hashCode()` в `Object`. С помощью алгоритма Марсальи — *xor-shift*, встроенной в JVM хеш-функции[^xorshift], — он выдаёт результат: хеш нашего объекта.

### `native`: тела на Java нет

Вопрос, который у меня возник:

> *не понимаю, почему не могу провалиться в метод `hashCode()`*

Провалиться не получится: у этого метода нет Java-кода. `native` значит, что тела на Java у метода нет, а реализован он на C++ внутри самой JVM (HotSpot), — IDEA просто нечего открыть. А Cmd+клик (Ctrl+клик на Windows и Linux) по имени там, где метод объявлен, — это действие *Go to Declaration or Usages*: на объявлении оно ищет уже не определение, а использования. Отсюда и подсказка «No usages found».

Аннотация `@IntrinsicCandidate` — ещё один слой. Она говорит, что HotSpot может заменить метод *интринсиком* — заранее написанным машинным кодом[^intrinsic]. С `hashCode()` JIT-компилятор так и делает: читает готовый хеш прямо из заголовка объекта и идёт в нативную функцию, только если хеша там ещё нет. Так что даже C++-реализация описывает не всё, что происходит на самом деле.

Где искать настоящую реализацию — в исходниках OpenJDK:

* [`jvm.cpp`, функция `JVM_IHashCode()`](https://github.com/openjdk/jdk/blob/jdk-25-ga/src/hotspot/share/prims/jvm.cpp#L622) — точка входа из `Object.hashCode()`;
* [`synchronizer.cpp`, `ObjectSynchronizer::FastHashCode()`](https://github.com/openjdk/jdk/blob/jdk-25-ga/src/hotspot/share/runtime/synchronizer.cpp#L989) и `get_next_hash()` рядом с ней — здесь хеш генерируется и записывается в заголовок объекта. Как именно — ниже, в разделе про identity hashCode.

### Реализация через `Objects.hash()`

Переопределяем (обязательно вместе с `equals()`):

```java
@Override
public int hashCode() {
    return Objects.hash(salary, position);
}
```

Тут всё гораздо проще: вызываем `Objects.hash()` и подаём туда те поля, по которым сравниваем в `equals()`. **Именно те же самые:** если поле участвует в `hashCode()`, но не в `equals()`, равные объекты получат разные хеши, и контракт сломан.

В случае наследования:

```java
@Override
public int hashCode() {
    return Objects.hash(super.hashCode(), grade);
}
```

`Objects.hash()` внутри выглядит очень просто:

```java
public static int hash(Object... values) {
    return Arrays.hashCode(values);
}
```

Из-под себя он вызывает `Arrays.hashCode()`, который уже показывает реальную логику работы:

```java
public static int hashCode(Object[] a) {
    if (a == null)
        return 0;

    int result = 1;

    for (Object element : a)
        result = 31 * result + (element == null ? 0 : element.hashCode());

    return result;
}
```

Мелкая деталь на будущее: `Objects.hash()` принимает *varargs*, а значит, на каждый вызов создаётся массив, и примитивы упаковываются в обёртки. В горячем коде это лишняя работа, поэтому там `hashCode()` пишут руками по той же формуле `31 * result + …`. А для [`record`](../Новые%20версии%20Java/Records.md) компилятор генерирует и `equals()`, и `hashCode()` сам — по всем компонентам.

### Почему именно 31

Никакой магии, просто удачное число:

* **Оно нечётное.** У произведения на чётное число младший бит всегда ноль: по сути, это ещё и сдвиг влево. При каждом шаге в младших битах копятся нули, а при переполнении `int` старшие биты просто теряются — вклад первых полей постепенно вымывается из результата. С нечётным множителем такого нет.
* **Оно простое.** Считается, что простой множитель лучше перемешивает биты и хуже «резонирует» с закономерностями во входных данных. Это скорее традиция, чем строгая математика: главное здесь всё-таки нечётность. Почему простые числа хороши в хеш-функциях, понятно объяснено в [главе 6.3 книги hello-algo](https://www.hello-algo.com/ru/chapter_hashing/hash_algorithm/) — там, кстати, мультипликативный хеш написан ровно как `hash = 31 * hash + c`.
* **Его дёшево умножать:** `31 * i == (i << 5) - i` — сдвиг и вычитание вместо умножения. Современная JVM делает такую замену сама.

Та же формула сидит в [`String.hashCode()`](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/lang/String.html#hashCode()): s[0]·31ⁿ⁻¹ + s[1]·31ⁿ⁻² + … + s[n−1], где n — длина строки. В Javadoc она записана через `^`, но там это степень, а не XOR из Java. Отсюда классический пример коллизии: у строк `"Aa"` и `"BB"` одинаковый хеш — `2112`.

### Хеш в `toString()`

Кстати!

Когда мы пишем

```java
System.out.println(programmer);
```

без переопределения `toString()`, то получим что-то вроде:

```text
com.username.src.equalshashcode.Programmer@e580929
```

Где `e580929` — это не что иное, как шестнадцатеричное представление хеша нашего объекта, поскольку вызывается `toString()` из `Object`, который выглядит так:

```java
public String toString() {
    return getClass().getName() + "@" + Integer.toHexString(hashCode());
}
```

Причём `toString()` вызывает именно `hashCode()`, а не какой-то отдельный «системный» хеш. Если мы переопределили `hashCode()`, после `@` будет уже наш, переопределённый хеш.

### Identity hashCode

А вот если `hashCode()` не переопределён, после `@` стоит *identity hashCode* — «хеш личности» объекта, а не его содержимого. Это тот самый нативный `hashCode()` из `Object`.

Популярный миф — что это адрес объекта в памяти. **Нет.** [Сборщик мусора](../../04%20JVM%20и%20производительность/Память%20JVM%20и%20сборка%20мусора/Сборка%20мусора%20—%20принципы%20и%20поколения.md) постоянно двигает объекты: из Eden в Survivor, в Old, при уплотнении. Адрес меняется, а `hashCode` по контракту меняться не должен. Поэтому HotSpot делает так:

1. Пока `hashCode` никто не спросил, его у объекта нет.
2. При первом вызове JVM генерирует случайное число тем самым xor-shift Марсальи — у каждого потока своё состояние генератора, чтобы потоки не мешали друг другу.
3. Число обрезается под биты, отведённые в заголовке объекта (*mark word*), и записывается прямо туда.
4. Все следующие вызовы просто читают значение из заголовка, поэтому хеш не меняется до конца жизни объекта, куда бы его ни переносил GC.

Режим «вернуть адрес» в JVM тоже есть (`-XX:hashCode=4`), но это экспериментальный флаг, по умолчанию стоит `5` — xor-shift. Все режимы видно прямо в [исходнике HotSpot](https://github.com/openjdk/jdk/blob/master/src/hotspot/share/runtime/synchronizer.cpp) — функция `get_next_hash()`.

Достать identity hashCode можно, даже если `hashCode()` переопределён, — через `System.identityHashCode(obj)`:

```java
Programmer a = new Programmer(1000, "Java");
Programmer b = new Programmer(1000, "Java");

System.out.println(a.hashCode() == b.hashCode());                         // true — наш hashCode() по полям
System.out.println(System.identityHashCode(a) == System.identityHashCode(b)); // почти наверняка false — это два разных объекта
```

На identity hashCode, например, построена `IdentityHashMap` — карта, которая сравнивает ключи через `==`, а не через `equals()`.

## Как это всё работает в `HashMap`

Теперь главное — зачем вообще нужен этот контракт. Когда мы кладём ключ в [`HashMap`](../Коллекции/HashMap%20—%20устройство,%20коллизии%20и%20ресайз.md) (или элемент в `HashSet`, который внутри и есть `HashMap`), происходит следующее:

1. Берётся `key.hashCode()` и перемешивается: `h ^ (h >>> 16)` — старшие биты подмешиваются к младшим.
2. Из хеша получается номер *бакета*: `(n - 1) & hash`, где `n` — размер таблицы (всегда степень двойки).
3. В бакете `HashMap` идёт по элементам и для каждого проверяет: совпадает ли хеш, и если да — тот же ли это объект (`==`) или равный (`equals()`).

То есть сначала дешёвое сравнение чисел, и только при совпадении хеша — дорогой `equals()`.

### Переопределили только `equals()`

```java
Programmer a = new Programmer(1000, "Java");
Programmer b = new Programmer(1000, "Java");

a.equals(b);                    // true — equals() переопределили

Set<Programmer> set = new HashSet<>();
set.add(a);
set.add(b);
set.size();                     // 2 — а ждали 1
set.contains(new Programmer(1000, "Java"));   // false
```

`hashCode()` остался из `Object`, у `a` и `b` разные identity-хеши, они почти наверняка попадают в разные бакеты, и до `equals()` дело просто не доходит. Получаем дубликаты в `Set` и `get()`, который ничего не находит.

Все четыре варианта разом:

| Что переопределили | Что будет в `HashSet` |
|---|---|
| Ничего | Каждый объект уникален — равенство по ссылке. Нормально для сервисов и бинов, но не для объектов, которые сравнивают по содержимому |
| Только `equals()` | Равные объекты обычно попадают в разные бакеты — дубликаты, `contains()` и `get()` не находят «такой же» объект |
| Только `hashCode()` | Равные объекты в одном бакете, но `equals()` по ссылке говорит «разные» — дубликаты остаются |
| Оба | Работает как задумано: один элемент на одно значение |

### `hashCode()` всегда возвращает константу

```java
@Override
public int hashCode() {
    return 42;
}
```

С точки зрения контракта всё законно: равные объекты дают равные хеши. Но все элементы падают в один бакет, и `HashMap` превращается в список: каждый `get()` и `put()` перебирает всё подряд через `equals()` — `O(n)` вместо `O(1)`. С Java 8 бакет, в котором набралось больше 8 элементов (при размере таблицы от 64), превращается в красно-чёрное дерево, и становится `O(log n)`. Но дерево упорядочивает ключи через `compareTo()`, а если ключи не `Comparable`, порядок у него почти случайный, и толку немного. Так что константа — это рабочий, но очень медленный `hashCode()`.

Контракт — это минимум. Хороший `hashCode()` ещё и раскидывает разные объекты по разным числам как можно равномернее — ровно про это третий пункт документации: разные хеш-коды для неравных объектов могут повысить производительность [хеш-таблиц](../../02%20Алгоритмы%20и%20структуры%20данных/Множества%20и%20словари/Хеш-таблицы%20—%20HashSet%20и%20HashMap.md).

### Изменили поле ключа после `put()`

```java
Map<Programmer, String> map = new HashMap<>();
Programmer key = new Programmer(1000, "Java");
map.put(key, "команда платежей");

key.setSalary(2000);            // поле участвует в hashCode()

map.get(key);                   // null
map.containsKey(key);           // false
map.size();                     // 1 — запись никуда не делась
```

Запись лежит в бакете, который вычислили по старому хешу, а ищем мы уже по новому — и смотрим не в тот бакет. Объект «потерялся»: достать его по ключу нельзя, а память он занимает.

**Отсюда правило:** ключи `HashMap` и элементы `HashSet` должны быть [неизменяемыми](Неизменяемые%20объекты.md) — `String`, `Integer`, `record`, свои immutable-классы. Или, как минимум, поля, которые участвуют в `hashCode()`, не должны меняться, пока объект лежит в коллекции.

### Коллизии и `TreeMap`

Если с хешами всё плохо — коллизий много или хороший `hashCode()` не написать, — есть [`TreeMap` и `TreeSet`](../Коллекции/Map%20—%20LinkedHashMap,%20TreeMap,%20EnumMap%20и%20IdentityHashMap.md). Они вообще не используют `hashCode()` и `equals()`: ключи сравниваются через `compareTo()` (или переданный [`Comparator`](../Коллекции/Comparable,%20Comparator%20и%20PriorityQueue.md)), и любая операция гарантированно стоит `O(log n)`.

Тут своя ловушка: `compareTo()` должен быть согласован с `equals()`. Классический пример — `BigDecimal`:

```java
BigDecimal x = new BigDecimal("1.0");
BigDecimal y = new BigDecimal("1.00");

x.equals(y);        // false — у них разный scale
x.compareTo(y);     // 0

new HashSet<>(List.of(x, y)).size();   // 2
new TreeSet<>(List.of(x, y)).size();   // 1
```

Один и тот же набор чисел даёт разный размер множества в зависимости от реализации.

## Когда можно не переопределять

Переопределять `equals()` и `hashCode()` нужно тогда, когда у объекта есть смысловое равенство: два разных объекта могут описывать одно и то же — деньги, координаты, программиста с конкретными данными. Такие объекты называют *value-объектами*. Не нужно переопределять, когда каждый объект уникален сам по себе и равенство по ссылке и есть правильное:

* **сервисы, контроллеры, Spring-бины, синглтоны** — экземпляр один, сравнивать нечего;
* **`enum`** — каждое значение существует в одном экземпляре, `equals()` там и так `final` и сравнивает по ссылке;
* **объекты-«личности»** вроде `Thread` или соединения с базой — два разных соединения не равны, даже если настроены одинаково;
* **`record`** — компилятор уже сгенерировал `equals()` и `hashCode()` по всем компонентам;
* **наследник**, который не добавляет полей в сравнение, — ему достаточно `equals()` родителя.

## Что имеем по итогу

`equals()` и `hashCode()` работают примерно одинаково и примерно по-разному. `hashCode()` отдаёт `int` — результат хеш-функции, а `equals()` сравнивает объекты по ссылке (и/или по полям, если мы переопределяем метод, что необходимо в большинстве случаев).

**У равных по `equals()` объектов обязан быть одинаковый `hashCode`, а вот одинаковый `hashCode` ещё не значит, что объекты равны.** Поэтому в хеш-коллекциях сравнение начинается с `hashCode()` — потому что он быстрее. А когда `hashCode` совпал — это не гарантия того, что сами объекты одинаковые, а лишь указание на то, что надо перейти к следующему этапу проверки и вызвать `equals()`, который уже однозначно скажет об «одинаковости» объектов.

Почему сразу не начать с `equals()`? Потому что чаще всего объекты разные, и задача сравнения чаще заканчивается `false`, чем `true`. А значит, можно воспользоваться более быстрым `hashCode()` ради тех самых 80% случаев и пренебречь скоростью остальных 20%. В написании кода это стоит учитывать и строить логику от неравенства быстрее, чем от равенства, поскольку равенство «дороже», чем неравенство.

[^getclass]:
    **Почему `getClass()` в родительском `equals()` возвращает класс наследника.**

    Вопрос, который у меня возник:

    > *мы же вызываем метод родительского класса из `MiddleProgrammer`, а `getClass()` вызывается в коде родителя — значит, и `getClass()` вызывается у родителя?*

    Здесь смешались две разные вещи: **чей код выполняется** и **на каком объекте он выполняется**.

    `super.equals(obj)` меняет только первое: выполняется код метода `equals()`, написанный в `Programmer`. Объект остаётся тем же. Никакого отдельного «объекта-родителя» внутри `MiddleProgrammer` нет. Есть один объект, у которого есть и поля родителя, и поля наследника.

    Поэтому, когда внутри родительского кода выполняется `getClass()`, по сути это `this.getClass()`, а `this` — тот же самый объект `MiddleProgrammer`.

    **Аналогия.** Вы, Вася, работаете по инструкции, которую написал ваш отец. В инструкции есть строчка: «Назови своё имя». Вы читаете её и говорите «Вася», а не имя отца. Инструкция отцовская, а выполняете её вы. Здесь всё так же:

    * инструкция — это код `equals()` из `Programmer`;
    * исполнитель — это объект `MiddleProgrammer`;
    * строчка «назови своё имя» — это `getClass()`.

    **Что делает `getClass()`.** Он объявлен в `Object` как `final`, его никто не переопределяет. Он не знает, в каком классе написан вызов. Он просто смотрит на объект, на котором его вызвали, и возвращает его настоящий класс — тот, что был указан при `new`. Это можно проверить:

    ```java
    class Programmer {
        void whoAmI() {
            System.out.println(getClass().getSimpleName());
        }
    }
    class MiddleProgrammer extends Programmer {}

    new Programmer().whoAmI();          // Programmer
    new MiddleProgrammer().whoAmI();    // MiddleProgrammer
    ```

    Метод `whoAmI()` написан только в родителе, а печатает разное: результат зависит от того, на каком объекте его вызвали.
