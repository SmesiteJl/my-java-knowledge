# Идемпотентность: idempotency key и дедупликация

> [!NOTE] Тема в работе
> Статьи по этой теме пока нет. Вот вопросы, на которые она ответит.

* Почему retry без идемпотентности создаёт два платежа, два заказа, два события
* Идемпотентный ключ в каждом запросе и дедупликация на границе сервиса
* Идемпотентность: повтор операции не создаёт нового результата (повтор оплаты — не вторая оплата)
* Как достигается: идемпотентный ключ и дедупликация
* Четыре источника повторов и ключ для каждого: Idempotency-Key, paymentId, event_id вебхука, message_id
* INSERT … ON CONFLICT DO NOTHING и request_hash: повтор, новый запрос, 422 при другой корзине
* Одновременные одинаковые запросы и откат первой транзакции; срок хранения ключей
* Idempotency key на попытку записи: тот же ключ → тот же appointmentId, тот же ключ с другими данными → 422
* Уникальный индекс по slot_id для активных статусов как гарантия против двойной записи; проверка в Schedule Service — только быстрый предварительный отказ
